# Historical k957 0.13.0 development plan

This is a retained historical design note. Its baseline and pending items do not describe the current release; use the root README and current development/test reports for present capabilities.

This plan records the review of k957 0.12.0 and the work required for the
zero-argument "full mode" workflow (`collect`, `verify`, `analyze`) and for
forensically sound RAM acquisition and analysis. Items are ordered by impact
(P0 highest). Each item lists its acceptance criteria. Checkboxes are updated
as work lands.

Go standard library only; CLI in `cmd/k957`, all logic in `internal/core`.

## 2. Target behavior

### 2.1 `k957 collect` (no arguments) = full mode

Equivalent to `k957 collect --full`. Collects everything the application
technically supports on the current OS, in RFC 3227 order of volatility:

1. **Memory** — physical RAM image (see 2.4).
2. **Live system state** — all system snapshot sources (processes, sessions,
   sockets, network, mounts, kernel/modules, event log XML exports on Windows).
3. **Artifacts** — a built-in OS artifact profile (logs, persistence
   locations, account databases without password hashes, shell histories,
   hosts/resolver, scheduled tasks), plus any `--root` given.

Layout (created in the current working directory):

```
output/
  <hostname>/
    <YYYYMMDDTHHMMSSZ>/
      evidence.k957        signed k957 evidence package (snapshots + artifacts)
      memory.lime          physical memory image (LiME) or memory.raw (external tool)
      memory.json          memory acquisition record (k957-memory/1)
      collection.json      acquisition record binding all artifacts (k957-collection/1)
      collection.sig       Ed25519 signature over collection.json bytes
      signing.pub          public key (hex) used for both signatures
      SHA256SUMS           coreutils-compatible hash list for third-party tools
      reports/<timestamp>/ derived analysis output (added later by analyze)
```

- Host name is sanitized to `[A-Za-z0-9._-]`; timestamp is UTC, filesystem safe.
- Signing: operator `--sign-key` if given, otherwise a fresh per-acquisition
  Ed25519 key whose private half is discarded after signing. The fingerprint is
  printed to stderr so it can be recorded independently (the embedded key only
  proves internal consistency, not authenticity).
- Defaults: case `AUTO-<host>-<timestamp>`, operator = OS user, scope =
  "Full automatic triage of <host>", timeout 4h, limits 256 MiB per file,
  8 GiB total, 100,000 files. Every default can be overridden by flags.
- Overrides: `--case --operator --scope --sign-key --root --timeout --max-*`,
  `--output-dir`, `--system=false`, `--artifacts=false`, `--memory=false`,
  `--memory-tool`, `--memory-tool-arg`, `--memory-limit`, `--reserve`.
- Absent profile paths are listed in the record, not treated as failures.
  Permission problems remain issues and make the acquisition `partial`
  (the record states whether the collector ran privileged).
- Exit code follows the existing contract: 0 complete, 1 partial or failed.

### 2.2 `k957 verify` (no `--in`)

Discovers every `output/<host>/<timestamp>/` directory and verifies each:
collection signature, embedded/`signing.pub`/optional `--trusted-key` match,
every listed artifact (size, SHA-256, SHA-1, MD5), the full evidence package
(`Open` with the collection key), memory image structure against
`memory.json`, and `SHA256SUMS`. Directories without a record (interrupted
acquisition) fail. Prints one JSON document; exit 1 if any collection fails or
none exists. `verify --in` keeps its existing behavior.

### 2.3 `k957 analyze` (no `--in`)

For every discovered collection: verify first (never analyze unverified
evidence), analyze the package, analyze the memory image, and write
`reports/<timestamp>/` inside the collection with every supported format:
`report.html`, `analysis.json`, `findings.csv`, `timeline.csv`,
`correlations.csv`, conditional `network.csv`/`captures.csv`/
`windows-events.csv`, new `memory.csv`/`memory-hits.csv`, the masked
`shared/` report, the effective `rules.json` and `verification.json`.
Uses a built-in triage rule set unless `--rules` is given. Analyze with
`--in` keeps its existing behavior.

### 2.4 RAM acquisition (standards alignment)

- **Linux (native):** physical `System RAM` ranges from `/proc/iomem`, read
  through `/proc/kcore` PT_LOAD segments using their physical address field
  (the AVML method). Output in **LiME** format (per-range 32-byte header,
  magic `0x4C694D45`, version 1), readable by Volatility 3 (`LimeLayer`),
  Volatility 2 and other LiME-aware tools. Unreadable pages are zero-filled
  and counted; unmapped gaps are recorded. Requires root.
- **Windows / other:** external acquisition tool (e.g. WinPmem, AVML) via
  `--memory-tool` with `{output}` argument placeholder; on Windows a
  `winpmem*.exe` beside the executable or in `tools/` is used automatically.
  The tool's SHA-256 is recorded. Format (LiME or raw) is detected.
- **macOS:** no native method (SIP/kernel restrictions); recorded as
  unsupported unless an external tool is supplied.
- **Integrity and documentation** (ISO/IEC 27037, NIST SP 800-86,
  RFC 3227): single-pass SHA-256 (authoritative) plus SHA-1 and MD5 for
  interoperability; start/end UTC, host, kernel release, method, source,
  ranges, gaps, unreadable pages, operator, case, tool version; capacity check
  before writing; image signed via the collection record; image written once,
  fsynced, never modified; memory captured first.
- **Analysis:** LiME structure validation, range/coverage/zero-page
  statistics, Linux kernel banner extraction (for symbol selection),
  literal rule hits (ASCII and UTF-16LE, case-insensitive) with physical
  addresses, bounded URL indicators, plus ready-to-run Volatility 3 commands.
  In-process process/kernel structure parsing is out of scope (external tools).

## 5. Review

Implemented as specified. `k957 collect` with no arguments is full mode and
writes `output/<hostname>/<UTC timestamp>/`. `verify` and `analyze` with no
`--in` cover every collection there. Linux memory is LiME v1. A read error
keeps the acquired prefix. Explicit `collect --root --out` behavior is
unchanged.

Validation on Linux AMD64, Go 1.26.8:

- `gofmt -l cmd internal` clean
- `go vet ./...` clean
- `go test -count=1 ./...` passed
- `go test -race -count=1 ./...` passed
- `python3 scripts/full_integration.py` passed (layout, Ed25519, SHA256SUMS,
  LiME physical address, reports, tamper rejection)
- `bash scripts/build.sh` built all six release targets
- statement coverage 88.2% (`go test -coverprofile=coverage.out ./...`)

A privileged container with the host PID namespace acquired every `System RAM`
range (33,679,503,360 bytes, six LiME ranges, collection status `complete`).
The first header was magic `0x4C694D45`, version 1, and its address matched
`memory.json`. The image was deleted afterwards. Volatility 3 is not installed
here, so it was not run. macOS native capture and physical disk imaging stay
out of scope.
